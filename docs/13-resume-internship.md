## 一、职责总述

聚焦企业内部多部门（人事 / 风控 / 财务 / 招采）流程智能化，主导设计并实现多智能体编排框架，统一承接异构业务任务：按复杂度与场景自动路由、任务拆解、多策略执行、知识检索、Token 成本治理与全链路可观测。目标是把重复性业务任务改造成可编排、可重试、可恢复、可评审的 Agent 工作流，并沉淀可复用的企业级 Agent 底座。

## 六、核心工作要点技术解析（面试答法）

> 本节对应“二、核心工作与可核实成果”的 5 个要点，按“为什么这样做、内部怎么实现、防错与边界、容易被追问什么”展开；存在量化指标的点，在解析后单独补充“量化成果”。

### 6.1 多策略路由与复杂度评分

**一句话总结：** 先算复杂度，再结合业务场景选策略，每次路由决策都带可解释因子，而不是黑盒拍脑袋。

**为什么做这一层：**
- 企业请求差异很大：人事高频单跳问答、风控合同审查多步骤、招采流程咨询可能拆成多节点。全部走 React/DAG，延迟与 Token 成本高；全部走 Simple，复杂任务质量不稳定。
- 借鉴 Shannon 的 Router -> Strategy Workflow -> Pattern -> Activities 分层思想，把“选策略”从执行器独立出来，后续既能加规则、加评测，也能平滑替换为模型路由。

**内部实现：**
- ScorerV2 从文本长度、连接词命中、步骤词命中、工具词命中、React 标记命中、是否带部门上下文等工作区特征中提取结构化特征，按权重求和并封顶 0.95，分数越高越偏复杂策略。
- 路由优先级为：显式策略 > 业务场景 > 通用规则。hr_policy_qa 分数低于 0.30 且无 React 标记时默认 Simple + RAG；risk_contract_review 走 DAG；通用请求按通用阈值 0.30 分流 Simple/DAG。
- 决策结果返回 strategy、complexity_score、confidence、reasons、subtasks、scenario_id；0.25-0.35 为低置信复核区间，Simple 且置信度低于 0.5 时预留升级到 React 的钩子，执行时通过 ROUTING_ESCALATED 事件真实升级。
- DAG 分支由 DecompositionPlanner 生成计划，PlanValidator 校验空计划、重复 id、缺失目标、非法工具/角色、缺失依赖、环依赖以及超过 2 层的嵌套深度。

**易被追问：**
- 评分规则是否适合所有部门？当前阈值按场景配置，可演进为可学习打分模型；路由评测底座已经具备回归能力。
- 分数与置信度为什么不合并？分数决定走哪档策略，置信度决定是否升级或人工复核，职责不同。

**量化成果：**
- 路由黄金用例 89 条，89/89 通过（实测，纯规则评测不消耗 LLM）。
- 评测输出总分、平均置信度、低置信数量与分部门准确率，每条用例的命中原因可落盘回看。

### 6.2 DAG + React 组合

**一句话总结：** 把 DAG 定义成执行拓扑、React 定义成节点行为，解决“固定流程里某个节点需要反复检索”的问题。

**为什么这样设计：**
- 风控审查是固定三阶段流程，但 t2 规则匹配需要根据 t1 识别出的条款反复检索资料，固定调用一次 RAG 偏弱。
- 若让 DAG 与 React 继续互斥，要么牺牲流程结构，要么牺牲检索灵活性；正交化后两者可组合。

**内部实现：**
- SubtaskSpec 增加节点级 strategy 字段，取值 direct / react / dag，PlanValidator 限制非法取值。
- DAGStrategy 按依赖分批，依赖就绪的节点用 asyncio.gather + 信号量并发执行（默认最大并行 4）；direct 节点先执行声明工具再单次 LLM，react 节点复用 React 工具循环，dag 节点递归执行嵌套 DAG，深度限制为 2 层。
- 整个流程共享同一个 TokenBudgetTracker，嵌套 React 节点累计用量，避免各节点各自记账导致预算失效；事件带 subtask_id / agent_role，SSE 能区分 t1/t2/t3 各自行为。
- 工具结果写工作区 dag/{subtask_id}/{tool}.md，所有子任务完成后由一次汇总 LLM 生成 answer.md。
- 风控场景实际为 t1 条款识别（contract_context）-> t2 规则匹配（react + rag_search/workspace_read）-> t3 审查清单生成；财务报销校验采用同样结构并预留人工复核闭环。

**易被追问：**
- 为什么限制嵌套深度？避免递归计划爆炸与上下文失控，当前 2 层已覆盖业务场景。
- 节点工具如何防误用？React 节点可声明工具白名单，模型调用白名单外工具时返回明确错误并继续循环。

**量化成果：**
- DAG + React 组合相关自动化用例通过，全量测试 62 项通过（实测）。
- Mock 黄金用例 30/30 通过（实测）见 6.5；真实模型 A/B 对比（通过率、Token 成本、P95 耗时）待验收回填。

### 6.3 真实 RAG 检索落地

**一句话总结：** 从关键词种子数据升级为“多格式导入 + 部门隔离 + 混合召回 + Rerank 精排 + 失败降级”的真实知识检索链路。

**内部实现：**
- 导入层支持 Markdown / TXT / PDF / Word / Excel / PPT，递归分块并带重叠，文档记录带 document_id、source、department、title、version、page 等元数据，manifest 统一索引。
- ChromaDB 支持本地持久化与 Server 模式，采用 cosine 距离，按部门使用独立 Collection（orchestra_hr / orchestra_risk 等）实现数据隔离。
- 检索层支持 hybrid / vector / keyword 三种模式：向量召回后与 BM25 关键词结果用 RRF（k=60）按名次融合，避免两种分数量纲不一致；可选调用 MaaS gte-rerank-v2 对融合结果精排，Rerank 异常时保留原结果，不让外部服务故障阻断链路。
- 中文采用英文词 + 中文二元组轻量词元化，BM25Okapi 未安装时退化为词元重叠计分，保持本地无重依赖也能跑。
- RetrievalRAGTool 把命中知识块写入工作区 rag/{source}，供后续节点和人工追溯；未命中或服务异常返回 success=false，Simple 策略会借机升级到 React 重新换词检索。

**易被追问：**
- 为什么用 RRF 而不是加权分数？向量距离与 BM25 分数量纲不同，直接加权不好定权重，RRF 只用名次融合更稳定。
- 部门隔离做到什么程度？目前是 Collection 级隔离，后续多租户可下沉到权限过滤与加密字段。

**量化成果：**
- 15 份演示文档完成 seed 入库，errors=[]（实测）。
- 真实链路样例查询 Top1 命中 hr/leave-policy.md，reranked=true，单次约 736ms（实测样例，非 P95）。
- hit@5 / MRR 等检索指标为占位，待黄金检索用例回填。

### 6.4 Redis Streams + 自研状态机工作流引擎

**一句话总结：** 用轻量自研方案补齐任务重试、崩溃补偿与多实例消费，让编排从“能跑”变成“可靠地跑”。

**为什么这样设计：**
- SQLite + 进程内 asyncio 后台任务缺少多实例认领、延迟重试与崩溃补偿；引入 Temporal/Redission 又偏重。
- 最终采用 Redis Streams + 自研状态机，保留统一 WorkflowDriver 接口，后续业务量增长可无缝替换更重的工作流系统。

**内部实现：**
- 状态机覆盖 PENDING -> ROUTING -> RUNNING -> SUCCEEDED，以及 RETRYING / WAITING_DEPENDENCY / FAILED / CANCELLED；终态不可再流转。
- 所有状态迁移通过 SQLite 原子 transition_task 认领，带 expected_statuses、version 与 attempt_count，重复 Worker 认领会因期望状态不符直接返回，避免双跑。
- Redis 模式写入命令流 orchestra:task:commands，Worker 用 XREADGROUP 并发消费、成功后 XACK；处理失败的消息留在 Pending Entries List，空闲超过 30s 由 XAUTOCLAIM 补偿给其他 Worker。
- Redis Streams 不原生支持延迟队列，所以重试用 Redis ZSET + Lua 原子弹出实现；RetryPolicy 默认最大 3 次、基础延迟 1s、封顶 60s、上下抖动 200ms。
- 应用启动时 recover 扫描所有未完成任务并续跑，RETRYING 到期后由调度循环拉起；Redis 连接失败时自动回退 SQLite 驱动，本地开发不依赖外部服务。
- 事件总线双写：SQLite 作为 SSE 读模型，Redis 事件流作为可观测副本；二级总线写失败只记日志，不阻塞任务流转。

**易被追问：**
- 为什么不用 Redisson？项目是 Python 技术栈，Redis ZSET + Lua 已覆盖延迟队列原子性，避免引入额外 Java 依赖。
- 是保证 exactly-once 还是 at-least-once？当前是 at-least-once + 幂等状态机认领，重复执行最终只认领成功一次。

**量化成果：**
- 全量测试 62 项通过（实测），覆盖状态机、重试策略、SQLite 重试/恢复、Redis ZSET 延迟队列与 Worker 消费闭环。
- 真实 Redis 验收：任务 succeeded、Pending 0、XACK 正常（实测）。
- 任务成功率 90%、故障恢复 10s 为占位口径，待验收回填。

### 6.5 高价值原型与全链路可观测

**一句话总结：** 用人事问答与风控审查两个极端业务原型验证框架，并让每一个执行环节都能通过 SSE 追踪。

**内部实现：**
- 人事制度问答：高频单跳默认 Simple + RAG；检索为空、检索失败或路由低置信时升级 React + RAG，评测允许 simple/react 两种策略通道通过。
- 风控条款审查：DAG 三阶段（条款识别 -> 规则匹配 -> 审查清单生成），其中规则匹配节点执行 React 反复检索；输出清单后进入人工复核闭环，复核结果可回流修正知识库。
- SSE 按事件 id 增量推送，事件覆盖任务创建、路由决策、策略开始、Agent 开始/完成、工具调用/完成、工作区更新、Token 更新、预算降级、重试调度、任务完成/失败；任务终态且事件发完后自动断开。
- Token 用量在 SQLite 中记录并按任务聚合，运行中间结果写入工作区，形成“过程可回放、来源可追溯、成本可统计”的闭环。

**易被追问：**
- 87% 代表什么？它是 30 条黄金用例验收目标（26/30）；当前 Mock 评测 30/30 为实测，真实模型业务通过率是待验收占位，不能当成已验证指标。
- 45min -> 8min 为什么标待验收？它描述首轮人工审查与系统辅助审查的预期收益，需在真实业务验收后回填。

**量化成果：**
- 30 条人事黄金用例 Mock 评测 30/30 通过（实测）。
- 真实模型业务通过率 87%、风控首轮审查 45min -> 8min 为占位指标，待项目验收后回填。
